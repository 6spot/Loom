# C3-T05：让综合事实和历史正文支持逐步多模型候选与对比

## 依据与执行边界

先读[本轮索引](README.md)及本叶涉及的当前规范。任务状态由现用管理工具维护；此处记录需求、接口、依赖和验收，不要求复制最终 PR/merge 元数据。开发阶段可以使用全新测试数据，退役实现无需兼容。有效来源、身份负约束、租约和发布保证仍须保留。

## 当前问题

当前 CHRONICLE_NARRATIVE_MODEL 由一个模型依次生成 facts/prose，每次整稿纠正独立实现。需要每个步骤可配一个或多个模型，并保留所有结果后对比，不重复发送无关步骤。

## 前置与文件归属

前置：[C3-T04 / #713](https://github.com/6spot/Loom/issues/713)。

下列路径均相对 `apps/chronicle/`（明确写出 `apps/`、`.github/` 或 `docs/tasks/` 的除外）；“新增”表示本任务交付，不假设文件已存在。

主改 `worker/narrative_stage.py`、`persistence/narrative_contract.py`、`narrative_store.py` 和相关模型配置；复用 T04 的通用 runner。更新 `docs/source-corroboration.md` 的执行合同。审核接受与发布策略归 T06。

## 实施步骤

1. 为 facts_generate、facts_compare/review、prose_generate、prose_compare/review 定义业务 adapter。单候选不发无意义的 compare 请求，但内容复核规则仍执行。
2. 固定所选完整已发布章节、catalog、来源关系和已经批准的状态。事实模型只在这些材料内提出具体结论；多个模型结果均保存并可单独查看。
3. 事实比较产出选用/整合理由、分歧及相关 conclusion/evidence 引用，不能按模型数量或 confidence 投票决定真伪。
4. 事实接受后才允许叙事生成。叙事只用被接受的结论和阶段；不得借“更流畅”加入新史实、抹掉分歧或删除后半段。
5. 纠错只重跑失败 adapter 及被改变输入影响的依赖步骤，保留先前完整结果。输入超限明确指出步骤与大小，不截断原文、不把摘要当完整来源。
6. 复用现有 jobs/model selection 的冻结配置原则。配置改动形成新 run，旧结果、来源和模型版本可追溯。

## 验收标准

- [ ] facts 使用两个模型、prose 使用一个模型的任务能够执行，结果与比较记录完整。
- [ ] 同书两传、转引、独立来源、未知依赖四种情况不被简单计票；不同阶段身份不被误判冲突。
- [ ] facts 有未解决异议时不运行 prose；prose 出现无依据新结论或漏阶段时不接受。
- [ ] prose 失败重试不重做已接受 facts；每次调用遵守全局 timeout 和冻结预算。
- [ ] 现有人工 review 仍可处理候选；在 T06 前不会绕过当前发布闸门。

## 验证方式

单元验证 adapter 输入/输出边界；用 PostgreSQL 运行多候选、分歧、超时恢复和两次审核场景。真实模型案例使用完整《周瑜传》及一份相关已固定来源，记录每步调用数和依据判读。

## 不在本叶内

不引入跨批次全历史，不扩人物详情 UI；不在读取页面时调用模型。
