# C3-T10：持久化全局历史版本并切换唯一公开读取入口

## 依据与执行边界

先读[本轮索引](README.md)及本叶涉及的当前规范。任务状态由现用管理工具维护；此处记录需求、接口、依赖和验收，不要求复制最终 PR/merge 元数据。开发阶段可以使用全新测试数据，退役实现无需兼容。有效来源、身份负约束、租约和发布保证仍须保留。

## 当前问题

T09 给出编排合同后，需要让真实数据库、审核和公开 API 使用该版本。不能保留“latest batch”和“latest edition”两个竞争的主历史入口，也不能每页把全历史 JSON 全部读出来。

## 前置与文件归属

前置：[C3-T07 / #716](https://github.com/6spot/Loom/issues/716)、[C3-T09 / #718](https://github.com/6spot/Loom/issues/718)。

下列路径均相对 `apps/chronicle/`（明确写出 `apps/`、`.github/` 或 `docs/tasks/` 的除外）；“新增”表示本任务交付，不假设文件已存在。

主改新增 `persistence/history_edition_store.py` 与应用迁移，`read_api/history.py`、`studio_jobs.py` / reviews 中的 edition 操作；按需改 `narrative_store.py` 的调用点。Rust 仍薄代理 `/api/v1/public/history*`，只在需要的新 Studio 子路由增加接线。与 T13/T15 的公共路由接线串行。

## 实施步骤

1. 使用应用表保存 immutable edition manifest、段落/结论/阶段索引和显式的 latest 指针/发布序号。正文可引用片段原记录；全局索引支持按 ordinal/ID 有界读取。
2. Studio 显式选片段创建 edition 草稿，列出接缝与重叠问题。复用已有任务/ReviewItem，只有处理完成且被接受的边界才可发布；不新增队列。
3. 发布在现有应用锁内重验基线、输入版本、接受记录与租约，原子提交 edition 和其索引。并发基线变化保留草稿并报冲突，不覆盖新内容。
4. `/api/v1/public/history` 默认返回最新 edition 元数据；带 version 的读取只读指定 edition。paragraphs/conclusions 复用现有路径和分页形状，按 T09 映射查回原来源。
5. 空环境返回真实空态；未知/未发布版本、错段、错结论返回明确 404/400，不退回最近批次。使用全新测试库，不编写旧书签兼容分支。
6. 接缝需要补充叙事时创建正常的受审稿件，只能引用两侧已批准事实；不能在读取时临时生成桥接文字。

## 验收标准

- [ ] PostgreSQL 空库发布 A+B 后可读全部；发布 A+B+C 后旧版仍只读 A+B。
- [ ] 300+ 段分页跨边界无遗漏/重复，状态和证据仍绑定正确片段/阶段；查询不加载整个全局 payload。
- [ ] 发布中途故障或丢租约无部分公开索引；两个发布者的基线冲突可见且可恢复。
- [ ] 未审核接缝、未知版本、无效位置被拒绝；公开 GET 无写入或模型调用。
- [ ] 公开主历史只有 edition 一套语义；来源章节/read 接口仍表示来源资料。

## 验证方式

必须运行 PostgreSQL 发布/回滚/并发/索引分页测试、history API/router 测试和受影响 Rust 代理测试。记录两次发布版本及可复验的跨边界请求。
