# C3-T06：实现可审计的自动内容通过与人工异常分流

## 依据与执行边界

先读[本轮索引](README.md)及本叶涉及的当前规范。任务状态由现用管理工具维护；此处记录需求、接口、依赖和验收，不要求复制最终 PR/merge 元数据。开发阶段可以使用全新测试数据，退役实现无需兼容。有效来源、身份负约束、租约和发布保证仍须保留。

## 当前问题

目标是通过校验与内容复核的稿件可自动推进，存在异议才交人工。当前综合发布必须有两次人工 approve。自动接受需要明确来源和证据，不能伪造一条人审记录或简单将状态改为 approved。

前置：[C3-T05 / #714](https://github.com/6spot/Loom/issues/714)。

下列路径均相对 `apps/chronicle/`（明确写出 `apps/`、`.github/` 或 `docs/tasks/` 的除外）；“新增”表示本任务交付，不假设文件已存在。

主改 `persistence/narrative_store.py`、内容 review/acceptance helper 与相关应用迁移，`worker/narrative_stage.py` 的接受分支；更新 `docs/source-corroboration.md`。先检查现有 historical_narratives 的“双人审 approve” trigger，不能只改 Python 绕过它。

## 实施步骤

1. 在规范中定义并冻结内容接受策略：结构/语义/引用均通过，要求的模型复核均完整结束并针对同一 candidate hash，所有异议有可验证处置，才允许 automatic receipt。
2. 接受记录区分 human 与 policy/model-review：记录 policy version、输入/稿件 hash、模型输出/意见 hash 和决定理由。发布读取这一条统一接受边界，不维持两种发布实现。
3. 结构合法但有歧义、来源矛盾、复核失败/缺失、修订后未复核或范围超限时建立异常 review，包含完整上下文、各模型原结果和待处理问题。
4. 人工修改产生新稿，重新校验并复核受影响内容；旧稿的接受不能用于新稿。重复、迟到、取消后决定或错 candidate hash 必须拒绝。
5. 将应用数据库 trigger/事务验证同步到新的可审计接受类型。统一发布锁、租约重验、正文/证据/导航原子提交全部保留。
6. 身份 same_entity/same_occurrence、负约束和需要人工的状态证据审核沿用已有 authority；内容自动通过不替代这些决定。

## 验收标准

- [ ] 无异议任务自动完成 facts→prose→发布，能追溯每条接受依据；没有伪造人工操作者。
- [ ] 单个 reviewer 异议、超时、缺返回、换稿、错误引用均进入明确异常或失败状态，不能成为多数通过。
- [ ] 人工编辑后原接受作废；解决问题后从正确步骤恢复，不重复成功的无关工作。
- [ ] 数据库层拒绝没有有效接受记录的发布，过期租约和并发发布失败不留半份公开正文。
- [ ] 现有身份/状态审核边界和负约束回归通过。

## 验证方式

必须有真实 PostgreSQL trigger/事务负例，不能只 mock store。用一组无异议和一组有史料冲突的完整来源结果验证自动/人工两条路径，并通读最终正文与依据。

## 不在本叶内

不以模型 confidence 设置“真实性阈值”，不新增独立审核队列，不自动合并历史身份。
