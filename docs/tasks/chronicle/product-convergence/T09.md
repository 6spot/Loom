# C3-T09：定义全局历史版本并实现跨批次编排的纯合同

## 依据与执行边界

先读[本轮索引](README.md)及本叶涉及的当前规范。任务状态由现用管理工具维护；此处记录需求、接口、依赖和验收，不要求复制最终 PR/merge 元数据。开发阶段可以使用全新测试数据，退役实现无需兼容。有效来源、身份负约束、租约和发布保证仍须保留。

## 当前问题

当前首页只取最新一次完整综合发布，每次最多 256 段。新批次会替代入口，无法在同一条阅读流继续读下一批。需要用多个已发布、经审核的叙事片段组成一个固定全局版本，而不是扩大单次模型输出。

## 前置与文件归属

前置：无；可在本轮清理交付后开始。

下列路径均相对 `apps/chronicle/`（明确写出 `apps/`、`.github/` 或 `docs/tasks/` 的除外）；“新增”表示本任务交付，不假设文件已存在。

新增规范 `apps/chronicle/docs/history-editions.md` 和纯合同/编排模块 `persistence/history_edition_contract.py` 及测试；更新 `source-corroboration.md` 的范围链接。此任务不写数据库、不改公开 HistoryPage。

## 实施步骤

1. 规范区分“已发布叙事片段”和“全局阅读版本”。全局版本保存有序片段引用、边界审核依据、全局段落/阶段/结论映射、精选导航和内容 hash；不复制另一份可编辑事实库。
2. 公共 locator 继续用系统 ID `{version, paragraph_id}`。version 固定完整 edition manifest；定义如何从片段版本+原段 ID 派生全局 hp_ID，所有结论和阶段引用也带来源作用域，禁止局部 ID 碰撞。
3. 编排器验证每段引用确实已发布、同一片段不重复纳入、局部顺序不改写、映射完整、入口可达、正文/状态/依据不串片段。
4. 不按年份盲排；未知日期保持审核确认的相对顺序。重叠覆盖、倒置或接缝不连贯必须成为待处理边界，不能直接自动拼接并称为流畅历史。
5. 定义追加、替换范围、并发基线变化与新版本规则：旧 edition 保持不变；新片段不得静默改变旧版本。段落范围不能仅用年份表达。
6. 本任务交付准确的 JSON 例子、错误码、纯编排函数及 T10/T11 用的统一 fixture。后续实现以此应用合同为准，任务说明不另立规格。

## 验收标准

- [ ] 至少 3 个片段、合计超过 256 段可形成固定有序版本；各片段仍受原单次生产容量保护。
- [ ] 两片段相同局部 paragraph/phase/conclusion ID 不发生串线。
- [ ] 未发布片段、丢失引用、重复片段、越界锚点、倒置/未处理重叠均明确拒绝。
- [ ] 未知年月不被补造；精选入口不因片段数量自动扩展成所有细节。
- [ ] 同一输入和排序生成相同 manifest/hash；追加只形成新版本。

## 验证方式

运行纯合同测试，逐项检查完整映射、边界异常和确定性；提供一份正常 manifest 和各类负例作为 T10/T11 的输入。

## 不在本叶内

不重新翻译全库、不合并全部内容成一次超大模型请求、不实现全球多地域排序推断。
