# C3-T19：用真实资料验收当前 Chronicle 产品闭环

## 依据与执行边界

先读[本轮索引](README.md)及本叶涉及的当前规范。任务状态由现用管理工具维护；此处记录需求、接口、依赖和验收，不要求复制最终 PR/merge 元数据。开发阶段可以使用全新测试数据，退役实现无需兼容。有效来源、身份负约束、租约和发布保证仍须保留。

## 当前问题

功能 Issue 关闭、fixture 或页面截图单独通过都不足以证明目标完成。需要在真实资料与当前模型配置下，从后台处理到公开连续历史、人物和保存背景实际跑通，并诚实区分内容质量与程序正确性。

## 前置与文件归属

前置：[C3-T08 / #717](https://github.com/6spot/Loom/issues/717)、[C3-T18 / #727](https://github.com/6spot/Loom/issues/727)。

下列路径均相对 `apps/chronicle/`（明确写出 `apps/`、`.github/` 或 `docs/tasks/` 的除外）；“新增”表示本任务交付，不假设文件已存在。

主改当前 acceptance 场景与 `corpus/second-round/acceptance/` 下的新证据目录，必要修复回到功能所有者模块。不得复制部署脚本或新增另一个验收入口；复用 T01 和 canonical development/deployment guides。

## 实施步骤

1. 使用新测试库与仓库固定版本的《周瑜传》《先主传》等完整章。记录 source hash、模型/profile、全局 timeout、各步骤尝试/耗时、接受记录和最终 publication IDs。
2. 跑一条可自动通过的内容、一条明确存在异议的内容；验证人工只处理异常，原文/模型结果齐全，修改后重新复核，失败能重试或换模型新执行。
3. 发布至少两个连续片段并组成一个 edition，从第一个读到第二个；再发布追加的新 edition，旧会话保持原内容。300+ 段容量由确定性 fixture 验证，真实样本不靠复制史料假造规模。
4. 从真实主历史进入周瑜人物页，核对不同阶段职位/效力，查看来源后原位返回；没有依据的状态如实缺省。
5. 上传已有背景，证明未保存不可见、保存后仅指定范围出现、停用回纸底、重启保留。全流程不得偷偷生成图片。
6. 检查精选锚点数量和意义：普通细节没有挤满侧轴；叙事段落连续、简体、无模型注释，大标题和资料卡不打断正文。
7. 每一失败写出复现、期望、实际、责任模块和证据，修复后只复测受影响范围。报告把“已通过”“真实质量待确认”“范围未实现”分开，不能把未做项写成完成。

## 验收标准

- [ ] 后台上传→分步多模型→比较/异常→发布→连续阅读实际完成，可逐步追溯。
- [ ] 至少 12 个原文核对点覆盖称谓、不同阶段身份、来源归属、矛盾和不确定性。
- [ ] 跨片段/时期无中断，人物/地点状态与证据正确，人物页往返恢复位置。
- [ ] 背景人工保存边界、停用、失败和重启行为全部成立。
- [ ] CI 与当前 gate 通过；真实浏览器/API/内容检查证据完整，剩余问题单列 Issue。
- [ ] 父任务只按实际已完成范围验收，不重新引入默认分支 Task Ledger PR/merge 对账。

## 验证方式

执行 T01 当前 gate 与涉及的真实服务/浏览器场景。复用各叶对同一代码/配置/样本已经成功的证据；修复、环境变化或新问题才补跑相关检查。真实模型调用必须保留可核查结果与费用/usage 是否报告的说明。

## 不在本叶内

不追求全历史覆盖，不扩大单次章节容量，不以虚构样本、只通过 schema 或 Issue 已关闭替代真实验收。
