# [C2-R2E] 多史料事实核对与连续历史叙事（增强阶段）

## 目标与轮次位置

总规划：[#547](https://github.com/6spot/Loom/issues/547)。关联第二轮 [#549](https://github.com/6spot/Loom/issues/549)、第三轮 [#550](https://github.com/6spot/Loom/issues/550)。

新增 **C2-R2E 增强阶段**，先建立多史料事实核对与综合历史正文的共用内容链路，再让第三轮消费其中的结论、适用阶段与阅读位置。R2 的原有来源阅读交付保留在原范围；本任务不重新判定其状态，也不等第三轮完成后才补这条基础链路。

本 Issue 负责这条内容链路的实现与验收。按用户授权直接交付后端、审核和正式阅读页；D01/D02 记录真实案例及共用合同，不再以新增实现任务作为开工前置。任务状态由当前任务管理工具维护，Issue/task 记录需求与验收标准。

## 为什么现在做

现有 R2 的 Reading Stream 以已发布来源 revision、原章节和译文 block 组织正文。现有 resolve/publication 主要确认是不是同一个人、同一次事件，保留各来源 Claim；它还不是完整的跨来源事实核对流程。

新产品需要综合多份资料，生成一份按时间正序连续阅读的历史叙事，并让人物与地点状态对应当前叙述阶段。如果先按旧 R3 的来源 stream/unit 接口完成状态存储、查询和页面，再补综合正文，会重复修改这些接口。

## 本阶段负责什么

1. **围绕具体历史问题核对资料。** 区分原文、来源主张、比较问题、候选结论及审核决定。相互支持、补充、矛盾、暂不可比较有不同表达。
2. **保留来源与判断边界。** 补充的是综合结论，不改写原书；未提到不是反证；后书抄引前书不计作独立见证；不同阶段、兼任和不同事件粒度不自动构成矛盾。
3. **改进审核组织。** 一次围绕一个问题查看各份完整必要上下文、来源归属、时间范围、建议结论与分歧；支持有范围的批量判断、逐条例外和页底保存并下一项。身份判断仍是独立决定，展示归组不产生身份等价。
4. **生成并发布综合正文。** 以有据结论和完整必要语境形成连贯历史，结论连接到具体来源原文。模型提出候选，结构校验、语义核对和人工审核分工清楚；阅读时只读已发布版本。
5. **提供新的叙事位置与下游关联。** 定义正文片段、主叙事阶段、人物/事件/地点、结论依据和固定版本的对应，供主阅读页与后续 R3 使用。保留来源阅读原含义，不悄悄复用旧 unit ID 表示另一种内容。
6. **接入正式前台。** 首页用重要时期/事件定位；正文正序连续，时期/事件只是锚点，不筛选前后内容。左侧时间轴，中间正文，右上附近事件；依据按需深入查看。直接替换正式页面，静态设计站和人工样例不作为产品交付。

## 与 R3 的交接

| 本阶段提供 | R3 消费或扩展 |
| --- | --- |
| 来源主张、结论、阶段、明确性理由与证据的共同语义 | 官职、爵号、效力关系以及地点状态的专门维度 |
| 新历史正文位置到适用阶段及结论的映射 | 随当前阅读位置显示紧凑的人物、地点当时状态 |
| 固定版本的结论、正文与依据读取 | 人物页对应阶段定位、身份演变和主历史往返 |
| 共用事实核对和发布机制 | 人物生平内容及其专门验收，不另建互不关联的史料库 |

本轮不以完整人物生平页或所有地点状态算法为门槛；这些进入修订后的 R3。背景上传/人工保存显示沿用独立范围；地图、任意关系图与反事实模拟不并入本阶段。

**并行按具体接口交接。** 共用契约确定后，R3 的独立状态算法、组件等可满足各自输入后并行；最终接线和真实验收依赖已发布综合正文与实际读取接口，不要求所有 R3 工作等整个增强轮结束。共享 schema、路由、controller、发布事务和 build/dist 明确单一文件所有者，顺序交接，不要求多分支。

## 案例、合同与实现边界

- [#659](https://github.com/6spot/Loom/issues/659) / C2-R2E-D01：真实多史料核对案例与预期结果。
- [#660](https://github.com/6spot/Loom/issues/660) / C2-R2E-D02：共用事实核对、叙事位置与审核发布契约，及 R3 交接/实现任务细分；正式定稿依赖 [#659](https://github.com/6spot/Loom/issues/659) 的可核对案例。

实现复用现有 IngestionJob、ReviewItem、租约和发布锁：显式选择已发布完整章 → 事实候选 → 逐条审核 → 完整叙事候选 → 正文与精选入口审核 → 不可变发布。页面消费新 history API；旧 Reading Stream 仍用于来源阅读。具体字段及容量由[共用合同](../../../../apps/chronicle/docs/source-corroboration.md)统一定义。

内部阶段按实际状态变化细分，前台 `entry_points` 是单独的编辑选择。抽取 Event 不自动进入首页或侧栏；任职、领有某地、未获任用等细节仍可在正文、人物经历和来源中保留。每个入口说明独立导航的理由，通常一组正文只选 1–5 项。

## 分段验收

### A：合同与真实案例

- [ ] 现有完整章中有可重定位的一致、补充、分歧、同源转引、阶段变化、未知和错误归组反例。
- [ ] 结论与原文、时间、归属、明确性之间的含义明确，模型不能直接发布“已证实”的真值。
- [ ] 新叙事位置与原来源 unit 的边界明确，并给出 R3 的共享输入及准确替代条款。
- [ ] schema、发布事务、路由、唯一阅读控制器和构建采用单一实现；不再要求另外拆任务才可交付。

### B：一组真实资料的内容闭环

- [ ] 使用现有《周瑜传》《先主传》等完整来源，经普通生产/审核/发布路径得到一段综合正文。
- [ ] 具体结论可查看对应原文与前后文；引用存在和格式正确不能代替语义支持。
- [ ] 补充信息、来源分歧、未知年月如实处理；两篇同属一书或互引资料不自动算独立印证。
- [ ] 新资料的结论须重新核对并发布完整新版本；旧 URL 的正文与依据不变。自动影响分析和跨批次拼接另行扩展。

### C：真实阅读与下游交接

- [ ] 事件/时期入口只定位；向下阅读继续越过该锚点范围，到真实已收录末尾才结束。所有批准阶段有正文覆盖，少量入口不意味着删减后半段历史。
- [ ] 正文、侧轴、附近事件与下游阶段上下文使用同一版本/位置；跳转、刷新、返回正确恢复。
- [ ] 正式页面可用，读到的数据确由流水线生成、审核并发布，不以内置样例代替。
- [ ] 人物状态 API 所需的阶段/证据交接可验证，完整身份算法和人物页由 R3 分别验收。

## 应用与交付边界

只使用 Chronicle application-owned persistence 和产品 API，遵守 Architecture Amendment 0006/0007。保留原始来源、稳定身份与有据同一性判断；本任务不赋予展示或模型新的 canonical/Runtime 权威。身份权威或注册边界如需改变，先走现有 Amendment 流程。

采用全新开发测试环境，不安排旧数据迁移或双生产链。按当前 docs/development/task-completion.md 交付，不增加默认分支 Task Ledger 的 PR/merge 对账步骤。
