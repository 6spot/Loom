# 多史料核对与综合叙事合同

本合同属于 Chronicle 应用层，承接用户确认的
[连续历史叙事](historical-narrative-design.md)。来源章节与旧 Reading Stream
继续表示原书译文；综合正文使用独立 `chronicle.historical-narrative/0.1`，
不能把原书顺序改名为历史时间顺序。

跨多个已发布综合批次的固定全局阅读版本遵守[全局历史版本合同](history-editions.md)：
本文件继续负责单批次事实、正文、状态和依据的审核边界；全局编排只引用这些
已发布片段，不复制或改写本合同拥有的事实。

## 生产与审核

沿用现有 IngestionJob、租约、ReviewItem 和 `present` 阶段。章节发布完成后，
操作员在 Studio 导入页显式选择完整已发布章节，固定当前 catalog 后创建只执行
`present` 的普通 job；其他阶段标为 skipped。不在每次章节导入后自动重写正文，
也不默选全库章节。配置综合模型后，该 job 先提出事实核对稿。
审核通过后再组织叙事，叙事经过第二次审核才发布。两个审核均属于现有 Studio
队列，状态不由 Markdown 或 Issue 是否关闭决定。

### 逐步多模型执行

综合任务的执行图固定为 `facts_generate`、`facts_compare`、
`prose_generate`、`prose_compare`。每个步骤可绑定 1–4 个已配置模型；单候选
不发送没有意义的 compare 请求，但仍执行本地 schema、来源、阶段和正文约束。
Studio 可通过 `GET /api/v1/studio/jobs/history/model-options` 查看不含凭据的
模型槽位，并在创建历史任务时提交 `model_selection`。选择只引用当前配置的
槽位和摘要；worker 将它与任务一起冻结，配置或提示合同变化必须创建新任务。

第一次执行会在既有 `ingestion_outputs` 中保存不可变的 narrative plan，绑定完整
章节、catalog、来源关系、已发布状态、模型 profile、步骤 schema、提示合同和
有限重试预算。每个模型槽位的完整请求、响应、receipt、校验结果和重试关系均
单独保存；成功结果按完整输入、步骤、round、槽位和模型 profile 的指纹复用，
不会因为重试而重新调用无关步骤。输入或纠错请求超过预算时报告步骤、实际大小
和上限，不截断原文或改用摘要。

多个 facts/prose 候选都交给 compare 步骤逐项说明选择、整合、分歧及
`conclusion_ids`/`evidence` 引用。来源的同书两传、转引、独立或未知关系，以及
不同阶段的身份状态，必须按冻结 context 解释；模型数量、confidence 或简单多数
不能决定史实。比较无法给出可解释唯一选择时保留全部候选并标记待人工处理，事实
审核仍是 prose 的前置闸门。prose 只接收已批准 facts；漏阶段、增加未审核结论或
不满足来源约束的完整结果留在审计记录中并拒绝进入下一步。现有两次 ReviewItem
审核、发布锁和 atomic publish 不变，T06 之前没有自动发布旁路。

核对稿 `chronicle.source-corroboration/0.1` 包含：

| 字段 | 含义 |
| --- | --- |
| `phases` | 有据的阶段及阅读先后；`year` 可为空，传统月份保存在文字 `period`，不伪装公历月 |
| `conclusions` | 具体核对问题、主体、阶段、结论、明确性、理由和每条依据 |
| `source_relations` | 同书、转引、依赖、独立或未知关系及判断理由；不按数量投票 |

结论 `dimension` 区分事件情况、官职、爵号、效力、地点行政归属、实际控制。
`phase_ids` 枚举结论适用的阶段；程序不把一次任命无限延续到后文，也不从参与
事件推导官职、阵营或控制权。兼任保存为多条结论，官职与爵号分维度。
取得领土、任免等状态变化前后须分阶段；阶段少不意味着导航更简洁。
R3 的专门时态算法可生产
这些明确适用阶段的事实，但不由这里的显示逻辑替代。

依据关系为 `support`、`supplement`、`contradict`、`background`、`incomparable`。
每条保留引用人／注者／原作者的 `attribution` 和解释。没有提到不是反证；不同
阶段的身份并不自动冲突；同书两传不算两个独立见证。“曹操在书信中称自己焚船”
与“曹操确实主动焚船”必须分别判断。身份同一性仍由已有 Resolution 决定。

`certainty` 只有 `clear`、`uncertain`。候选中的字段是建议，只有审核接受的具体
正文和理由可以发布。模型 confidence、来源条数、JSON 校验成功均不证明结论。
程序检查引用、版本、主体、阶段和范围；审核者检查表述是否得到语境支持。

完整 JSON 形状由 `persistence/narrative_contract.py` 的 schema 定义。
模型通过本次请求的 `entity_001`、`event_001`、`evidence_001` 短句柄引用既有
记录，程序按冻结 context 确定性地逐一编码／解码，只变换引用字段，不替换
正文、引文或局部结论 ID。未知句柄仍失败；这种映射不判断身份、不改变归并。
`source_relations` 使用来源句柄 `source_001`，不用 publication ID 充当来源名。
所有原文段落在生成上下文中完整保留，不以相邻几字代替整章。输入超过容量时
明确失败，不截断来源、跳过后章或把摘要冒充全章。

来源人物状态索引会在多个阅读段重复同一项。冻结 context 保留全部记录；
模型视图仅在同一来源内去除完整字段完全相同的重复状态。阶段、明确性、限定、
理由或 provenance 有任何不同均保留，跨来源不去重，不按名称合并状态。
这只是减少重复传输，不增加印证票数，也不缩短原章、译文或原文锚点。
不同状态项也会重复携带同一来源事实的 provenance。模型视图在确实减少体积时，
以该来源内的 `reviewed_person_state_sources` 表保存完整且完全相同的来源记录，
各状态用有序 `source_fact_refs` 引用；还原后与原 `source_facts` 逐项相同，
包括空列表、重复引用和全部字段。字段有任何区别就保留为不同记录，跨来源不
共用表或句柄。冻结 context、模型原始结果、已审核内容及发布合同不变；纠错仍
携带完整旧稿和诊断，超限不能靠删掉来源或已批准阶段继续。

## 叙事与位置

叙事候选按审核通过的 `phases` 正序组织段落，并至少用一段覆盖每个批准的阶段。
阶段定义本次正文范围，事实审核前每个阶段至少有一条适用结论；不能为修复其他错误而删除后半段历史，少量导航不意味着缩减正文。
每个自然文字片段关联一条或多条
结论，不要求逐句对应原文。叙事模型不得创造新的结论、阶段或状态事实。
事件词可关联已有事件，并区分发生、回顾、预叙、背景。入口指向确切段落，
不把事件／时期作为正文过滤条件；读过入口范围仍继续已发布后文。

`entry_points` 是首页、左轴和附近事件共同使用的精选导航，通常 1–5 项，最多
12 项，没有合适重点时允许为空。每项的 `reason` 解释其重要性、涵盖的发展和
为何不并入相邻入口。同一事件的筹备、交战和收尾共用入口；普通行动、任免和
往来不独立立项，确有重大转折意义时由编辑说明理由。名称指向具体历史进程，
不能使用“从这段读起”等占位文案。原始 Event、状态变化和内部 phase 均不会
自动升级为入口；零散事实保留在正文与检索。入口最终按正文顺序编译。
`event_text` 为正文中仅出现一次的简短事件称呼，只让这几个字触发预览；可以
为空，不能为形成链接而把整段正文高亮。事件入口必须指向实际发生段，不能
定位到仅回顾、预叙或背景提及处。

左侧公开时间轴使用独立的 `navigation`，与正文一并生成、编辑和审核，不新增
模型调用。每个区间含时间/时期 `label`、首末段落和 `items`。区间按正文顺序
连续覆盖全文；`items` 只能引用精选 `entry_points`，沿用其名称和选择理由，
在本区间内有序、不重复，全部精选位置必须出现。每区间允许 0–12 项，不为了
填满年份或区间额外编造事件。Studio 在编辑精选入口时同步这些定位项，不再
维护另一套“次级进展”。具体重要性由模型提案和人工通读判断；结构校验不
声称能判断历史重要性。

区间可表示年份、有依据的范围或时期；无法确定的 `label` 为 null，前台只保留
其在连续轴体上的阅读位置，不显示未知年代标题。未知年月不得补造，分组不
改变段落的真实阶段/状态。旧稿没有 `navigation` 时按相邻年份/未知时间段投影
时间刻度，只挂接已有精选入口；内部阶段名称不变成节点，不再补“从这段读起”。
旧稿的“年代未详”等纯未知时间标签公开显示为 null，原始发布记录保持不变。

首期读者语言统一为 `zh-CN`。翻译在保存段落及建立文字关联前转换为简体；
综合叙事、导航及状态说明在进入审核前同样规范化，模型原响应仍原样留存。
审核提交须保持简体。实体展示名称按简体显示，ID 和名称对应关系不变。
历史公开 API 可提供已发布内容的简体字形展示投影；原始发布记录、原文、
引文、原文坐标及其摘要始终保持原样，字形转换不增加史实或身份判断。

每个发布版本固定：输入 catalog、完整来源版本、两次审核决定、结论、正文、
时间分组、事件入口和人物地点资料。新综合位置是 `{version, paragraph_id}`，
URL 为 `/history/<sha256>/<hp_id>`，复用现有系统 ID，不生成标题别名。
`/history/<sha256>` 从该版本首段进入；旧查询参数地址校验后替换为新路径。
此处只调整访问地址，不引入 HTML 预渲染或其他 SEO 能力。
不借用来源 stream/unit 的身份。
来源引用继续使用其真实 `{publication_id, anchor_id}`。

网页只读已发布版本，滚动与打开网页都不调用模型。段落 API 按固定版本分页，
失效／未知位置明确报错，不能静默换成最新版本或按同一年份猜位置。
年份不明确时保留阶段顺序及原文标签，不能强补年份。正文末尾只代表当前收录
范围结束，不声称整个时期或人物生平已经结束。

## 发布与容量

候选及发布正文是不可变记录；审核保存最终接受文本及其摘要。后台以既有
发布锁与 job 租约提交完整版本，正文、结论和导航不能分步变为可见。模型请求
在数据库事务外进行，回写前检查租约。失败／重启采用已保存候选，不重复生成。
新增来源后旧版本仍可读，新稿必须重新核对；旧稿不能静默升级证据。

每次执行最多 3 次完整生成／纠正，纠正带完整旧稿及诊断，并保持同一完整来源。
普通 retry 会续用同一冻结 context 下最近一次失败稿及诊断；不同 context 不复用旧稿。
每次请求 hash、context hash、模型、原响应和校验错误写入原 `ingestion_outputs`。
每次生成保存独立递增序号；重复的模型响应也保留为不同尝试，不能因内容 hash 去重而续用错稿。
两个审核暂停会各占一次 claim，因此显式综合 job 的 `max_attempts=5`：两次审核
续跑加原有三次执行机会。运输重试和内容纠正不创造另一条生产队列。

事实批准请求必须精确列出所有最终结论的 `reviewed_conclusion_ids`。审核可以
修改、添加、拆分或移除候选结论，重新验证引用与阶段后保存最终内容。批准时
绑定原 candidate SHA；重复、迟到、已取消或版本不符的决定失败。驳回会记录
决定并取消本次 job；取消会把未完成的审核标为 dismissed，保留候选及审计。

发布锁后、编译后、写入后和最外层 checkpoint 提交前再次检查未到期租约。
任一失败必须连同发布记录和完成状态一起回滚。数据库 trigger 要求同一 job
两次 approve 的内容 hash 与发布对应，候选和发布表拒绝更新／删除。

首版限定一次至多 16 个完整章节、64 个阶段、256 条结论、256 个叙事段落；
单段至多 8192 个 Unicode code point，正文产物至多 2 MiB。超限返回明确错误，
需要调整生产范围。公开分页每页 1–50 段，不在前端累积无界 DOM。

当前首页仍选择一个固定的已发布综合版本。全局版本可以按
[全局历史版本合同](history-editions.md)引用多个生产片段，但旧版本保持可读、
片段接缝必须经过审核；无限规模窗口和跨地域排序推断仍不在首版。

## HTTP 接口

| 接口 | 范围 |
| --- | --- |
| `GET /api/v1/studio/jobs/history/sources?limit&offset` | 当前 catalog 下最新来源 revision 的完整已发布章节 |
| `POST /api/v1/studio/jobs/history` | `{catalog_sha, publication_ids[, model_selection]}` 显式创建综合任务 |
| `GET /api/v1/studio/jobs/history/model-options` | 当前综合任务可用的无凭据模型槽位 |
| 既有 Studio review decision / resume / retry / cancel | 两次审核、恢复与取消，共用鉴权和 control plane |
| `GET /api/v1/public/history[?version]` | 已发布版本的分组、精选入口与段数，未发布时 publication 为空 |
| `GET /api/v1/public/history/paragraphs?version&at\|start&limit` | 固定版本定位／分页正文 |
| `GET /api/v1/public/history/conclusions/{id}?version` | 结论、明确性及固定原文引用 |

公开正文及依据请求必须给出版本；非法、重复或未知参数不宽松回退。Rust 负责
公开路由与 Studio 鉴权，Python read API 委托 Chronicle persistence 读取，SQL
和迁移均限于已注册应用持久化边界。

## 前台与审核界面

首页列已发布叙事的时期／事件入口，主阅读页左轴、中间正文、右侧附近事件和
当时人物地点。单条状态使用实心／空心标记及明确／存疑文字；缺失保持缺失。
原文依据通过阅读资料深入查看。背景仍执行人工生成／上传、核验、保存后显示。

审核界面按具体问题展示各方依据，能够查看完整来源上下文。保存、驳回、返回
及下一项操作常驻可用；服务失败保留编辑。事实与正文的修订在相应审核阶段
进行并重新校验，不能凭一次“合并人物”按钮接受历史真实性结论。
