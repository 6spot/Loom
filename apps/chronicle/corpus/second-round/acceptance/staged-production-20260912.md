# 《先主传》分阶段生成与模型复核试验（2026-09-12）

**单次响应完成的问题有了可行方向，内容质量仍未通过。** Luna 在一次完整章
调用中返回译文，另一次调用返回提取结果；复核和汇总也都返回完整响应。
这次没有逐段调用翻译，没有重跑旧的巨型联合生成。模型复核和汇总仍出现
漏检、错引、误判，不能据此自动发布。

这是隔离的生成试验，只保存文件证据，没有产品 DB、审核、发布或部署操作。
正式 worker 的阶段持久化、可配置多模型和自动发布仍未实现。
[#586](https://github.com/6spot/Loom/issues/586) / #549 保持未验收，
[#681](https://github.com/6spot/Loom/pull/681) 保持 draft；不替代 R3 验收。

## 请求范围与用户澄清

同一完整《先主传》原章为 12,591 字符、86 个源块，旧联合契约有 41 个必需块。
本次保留整章及全部原注作为上下文，只把正文译入读者文本：36 个待译来源块，
正文 7,269 字符。范围中有 48 段显式 `〈…〉` 原注，另有一段跨块注释续文
`b_029`，两者合计 5,221 字符；纯原注块不进入翻译目标。

`b_029` 是前后《献帝春秋》嵌注的引文续接，由主持 agent 检查本章边界后
显式标记，不表示通用解析器已能识别所有注释边界。
原文、原注、坐标和这次边界决定全部保留在
[plan.json](staged-production-20260912/plan.json)。原注没有被删除，后续提取可用。

翻译模型一次返回 **52 个自然段、10,625 个译文字符**。自然段只是同一次响应的
排版，不是 52 个独立翻译任务。返回首尾及来源范围通过机械检查，但该检查不能
证明所有语义均已完整、准确翻译。

这次试验的输出仍带极小的 `{blocks:[{source_ids,text}]}` 结构，便于核对来源。
随后用户进一步明确：正式翻译节点只产出整章纯白话文本，连来源编号也由后续
程序/步骤处理。本次**没有另做纯文本 API 请求**，
[translation.txt](staged-production-20260912/translation.txt) 只是从已保存响应
导出的阅读样本，不是另一次生成，更不是已通过审核的正文。

用户确认的阶段保存、单/多模型配置、AI 先审和人工例外要求见
[讨论记录与拆分依据](../../../../../docs/tasks/chronicle/staged-production-discussion.md)。
整章来源译文也不等于多史料综合历史流，后者仍需既有综合叙事流程。

## 实际运行

使用 CPA 的 Responses 接口，执行代码版本为
`07c6c4044f2cfa2c4418df1b2d5e71c93772f47a`。临时 runner 复用该版本的
`ResponsesHTTPModel` 和 `chapter_contract.resolve_selection`；不把本地证据树
后续运输代码的版本混作实际执行版本。模块与 runner SHA 见 manifest。

每个节点最多一次 HTTP、无自动重试/纠错，设 600 秒总时长、4 MiB 响应限制。
HTTP 使用非流式；收到 keepalive 字节只表示连接活动，不表示已生成多少译文。
所有节点都明确返回 `completed`，本次无超时或残缺正文。

| 节点 | 模型 | 实际耗时 | 报告总 tokens | 机械检查与内容观察 |
| --- | --- | ---: | ---: | --- |
| 整章翻译 | Luna | 114.150 秒 | 34,715 | 结构、顺序、36 个目标覆盖通过；另有来源 hash 误标和内容问题 |
| 独立提取 | Luna | 124.013 秒 | 35,342 | 19 实体、8 事件、12 事实；5 条原文引用错误，另有主体/状态错误 |
| 译文复核 | Luna | 67.060 秒 | 41,103 | 返回 3 条意见；引用/覆盖通过，漏检及建议可靠性仍有问题 |
| 译文复核 | Sol | 208.692 秒 | 46,375 | 返回 15 条意见；2 条原文引用错误，发现多处 Luna 未报告的问题 |
| 复核意见比较 | Luna | 97.300 秒 | 37,452 | 18 条意见全部纳入 16 组；1 条引用错误，且存在错误裁决 |

翻译完成并保存后，提取与两路复核并行。比较等待两份复核报告保存后执行。
提取使用的是固定的未批准译文版本，事实要求仍以完整原文为依据；因此它是
待校正的候选，不能因并行完成而进入生产接受。改变译文后应重验受影响关联。

合计 **5 次模型请求 / 5 次 HTTP，服务报告 194,987 tokens**；账单费用未知。
仅翻译与提取两次为 70,057 tokens，其余用量来自复核和比较。多模型不是免费
提高准确率，本试验也没有证明它比旧流程更省总用量或已达到稳定完成率。
前后翻译范围、输出职责和审核步骤不同，不能用总数做等条件效率结论。

模型输出预算分别为 32,768、24,576、8,192、8,192、8,192。
Sol 这次报告输出 9,700（含推理 6,343），超过请求的 8,192；如实保留，不把
本地请求额度当作通道保证，也没有继续调查上游路由。

## 内容问题及多模型流程的实际限制

主持 agent 通读了全部 52 个译段，并保存
[独立译文问题记录](staged-production-20260912/host-review.json)。它包含 12 个
观察点，其中“请求出兵相助”只记为措辞疑点，不当作已经确定的实质误译；
这不是人类审核决定，也不是穷尽所有错误的金标准。

需要修正的具体例子包括：

- `b_017` 的“靈等還”承接朱灵，译文 `t_010` 却写成“关羽等人回来”。
- `b_015` 原注解释董承是献帝的丈人，译文仍按现代词义写成“舅舅”。
- `b_023` 原注明确“是時曹公在宛”，译文 `t_013` 把到宛的主语接成刘备。
- `b_047` 的“上官逆謀”译成霍氏谋反；“臣等以備”又被译成所有群臣也都是
  皇室近亲，改变主体及身份关系。
- `b_059` 的“臣父群”被凭空补姓为“刘群”。

两路复核及比较没有把这些问题全部解决：

1. 两个复核模型都查出朱灵/关羽问题；Sol 另查出宛县主语、上官氏等错误。
   但“coverage=checked”不代表真正查出全部错误。
2. Luna 的汇总虽然逐项覆盖了所有 18 条意见，却把 Sol 对宛县主语的有效纠正
   判为不成立，忽略了同章原注的明确说明。
3. 汇总把“會見使”改解释为“有使者来见”，可能在修正时引入新错误。
   它还赞同把“亡者日多”强改为死亡人数，而未建立充分的语境依据；该古词争议
   不能靠两次模型赞同当成已解决。
4. 比较响应仍有一条不能逐字定位的引文，按程序规则没有获得检查点。

完整的 [Luna 复核](staged-production-20260912/review-luna/result.json)、
[Sol 复核](staged-production-20260912/review-sol/result.json)、
[模型比较](staged-production-20260912/comparison/result.json) 以及
[主持 agent 对比较结果的核对](staged-production-20260912/host-comparison-review.json)
分别留存，没有用最终摘要覆盖少数意见或失败历史。

提取结果也需要语义核验，见
[独立提取问题记录](staged-production-20260912/host-extraction-review.json)：
`f_011` 的内容是曹丕称帝，`subject_ref` 却指向曹操；祖先血缘被分类成政治
效力；夷陵/夷道猇亭混成一个地点名；合并战事只有末段时间且时间引用不足。
输出的细节事件也不能直接成为前台锚点。引用存在、ID 存在、计数非空均不能
证明它们适合侧边人物状态或重大事件导航。

## 保存和恢复验证

[六项离线检查](staged-production-20260912/resume-verification.json) 全部通过，
新增 HTTP 为 0：

1. 同一翻译 spec 复用已保存结果。
2. 同一 Luna 复核 spec 复用已保存结果。
3. 改变 spec 拒绝旧检查点。
4. 改变输出内容，即使只追加空白，拒绝旧 hash。
5. 上游来源文件与固定 hash 不符，拒绝复用。
6. 已失败的提取阶段不静默重试，要求明确的新 attempt。

这些是临时文件检查点的验证，**不是正式 worker 的进程重启、DB 原子性、租约
接管或崩溃恢复验收**。本次未运行自动修正，未生成经过审核的新版译文，未测试
每个步骤的多候选生成，也没有把节点单/多模型选择做成产品配置。

## 证据与后续实现边界

[manifest.json](staged-production-20260912/manifest.json) 列出全部请求、响应正文、
检查结果、脚本、源版本和 SHA。原始 HTTP envelope 在私密试验目录内，已核对
大小、SHA、完成状态和 usage；入库只保留这些元数据，不包含凭据或私密 reasoning。
归档的 `*.py.txt` 是此次试验代码证据，不是第二套受支持的生产执行入口。

离线 [证据核验结果](staged-production-20260912/verification.json) 为 **234/235 项
通过、1 项失败**。失败项是本次初版试验准备的元数据问题：翻译 spec 的
`source_sha256` 实际填了规范化文本的 `normalized_sha256`，与原始文件 hash
不同。完整 plan 的 hash 及实际送入的整章上下文均核对一致，不是换错了原章。
该错误及两种 hash 见 [元数据复核](staged-production-20260912/metadata-review.json)；
原 spec/响应保持原样，失败检查没有被删除或放宽。正式契约必须分清、验证两种
hash，不能继承这个试验字段误标。其余检查涵盖归档 hash、schema、引用失败
重放、实际依赖/并行关系、意见覆盖、用量和恢复记录。

产品代码没有改动，因此没有借无关单测或浏览器 fixture 宣称内容通过。

下一步正式接入需要修改章节生产合同及产物版本，扩展现有任务/保存/审核路径，
将翻译、独立提取、逐项比较与有界修正分开。优先用程序提供的固定来源句柄
减少模型抄写长引文的错误，同时保留完整原文上下文和语义核验。
自动身份归并若改变当前人审权威，须先走已记录的 Amendment 变更点。
本报告只交付试验与结论，不把仍有错误的候选发布给读者。
